# Controlled pilot plan and operating guide

## Scope and go/no-go
**Permitted now:** one internal fictional workspace, two eligible fictional participant records, web-only rehearsal, one evaluator rubric per session, one complete improvement/transfer cycle, no sensitive data. The application remains an evaluation build. A real organizational pilot is **NO-GO** until authenticated hosting, approved data handling, named content review, and appropriate security/accessibility acceptance exist.

Suggested first journey: use **The unanswered duty call**, then **The alternate also cannot respond** after a documented correction. This tests a changed authority/dependency condition, not memorization of the same answer placement.

## Administrator quick guide
Open `#/pilot`. Leave the workspace on fictional data. Select the experience, inspect its source assumption/objective/role boundary, set a fictional site and mode, select Morgan or Jordan, and acknowledge the limits. Create an in-app assignment. Inactive Casey is excluded with a recorded reason. No external notification is sent.

Switch to the participant persona to use that assignment. Persona switching is a demonstration mechanism; it is not an invitation, login or permission grant to a real person. When the evaluator records a finding, assign a correction with owner, due date, measurable completion criteria and separate verifier. After the owner's evidence exists, create the explicitly linked transfer retest. Situation/handover currently have no authored transfer pair and cannot be closed using an unrelated one.

## Participant quick guide
Select your fictional persona, open Assignments and acknowledge/launch your task. Read the role, source and current artifacts. Produce the requested work. Drafts autosave after a short typing pause; submission freezes each work product. Pause deliberately before switching away. Refresh returns interrupted work paused; active time does not infer offline effort. Stop ends the attempt without inventing a failure score. Do not enter real names, contact details or operational data.

## Evaluator quick guide
Open Evaluate. Inspect the original artifacts and submitted work before selecting each criterion status. Each decision requires rationale and a work-product reference. Do not treat rule checks or response length as competence. Record what the evidence determined, the operational impact in the scenario, and an evidence-supported cause; Undetermined is valid. Later review changes append a revision. A participant may question a review; record the resolution before verification.

The test suite uses deliberately synthetic evaluator entries to test software behavior. Those entries are not professional approval. For actual evaluation, a named authorized human must make the decisions and calibration must be documented.

## Improvement owner and verifier quick guide
The owner records what changed and its supporting evidence against the action's completion criteria. Self-report changes status to ready for verification, not closed. A separate verifier inspects the original finding, owner evidence, materially different retest and latest evaluator review. Required retest criteria must be met; unrelated, incomplete, invalidated or appealed evidence blocks verification. A verification record retains all original links. Later contradictions require reassessment, not rewriting history.

## Program-owner view
Evidence trace separates assigned/eligible population, launches, completions, reviewed evidence and verification records. Each count links to underlying IDs. Inspect overdue actions, cause uncertainty and evidence class. Export the full trace for independent inspection. The JSON SHA-256 detects accidental change only; it is not an authenticated signature.

## Data handling, stop and recovery
Data stays in this browser's IndexedDB; legacy demonstration data is separate. Volatile mode explicitly warns that refresh/closing loses current memory. Export before closing or clearing a browser profile. Do not clear or reset corrupted storage; export the raw recovery record and preserve it. Browser backup import, automatic retention and legal hold are not implemented. No customer data is permitted.

For a real incident or confusion about whether a message is an exercise: stop the fictional session, exit the application, and follow the organization's actual approved process outside this tool. No automatic call, text or external dispatch can occur here. Raise software defects with the release SHA, view, minimal fictional reproduction and export only if it contains no sensitive information.

## Usability and learning protocol
Before involving a real cohort, obtain the required approvals. Then record baseline performance on an approved task, administer focused practice, assess delayed retention at an agreed interval, and use a changed transfer condition. Have two calibrated reviewers independently assess a sample, preserve disagreements, and record resolution. Do not claim a result from this design alone; no such participant data has been collected.

Measure separately: assigned and excluded population; launch/acknowledgment; completion; objective evidence; reviewer agreement; cause category; action age; verification and retest outcome; delayed retention; participant workload and accessibility. Record denominators, missing evidence and observation windows. No universal readiness percentage.

## Approval checklist
Internal fictional rehearsal: source/device boundary visible; no live providers; clean-state journey and recovery checks pass; exact build identified; exports inspectable; rollback exists. Customer use additionally needs a named sponsor/content reviewer/evaluator, authenticated hosting and data agreement, security approval, accessibility acceptance, participant consent and support/stop procedure. Names, signatures and dates remain unassigned until actually supplied.
